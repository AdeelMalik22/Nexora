# Backend Plan: Modular Monolith POS Platform

## 1. Goals
- One Django codebase serving many shops (multi-tenant).
- Shared core plus plug-in industry modules.
- Offline-first clients that sync safely, with no duplicate bills or lost data.
- Correct money and stock math, with a full audit trail.
- Ready to extract services later without a rewrite.

## 2. Tech Stack
- **Framework:** Django + Django REST Framework (drf-spectacular for API docs)
- **Database:** PostgreSQL
- **Cache, queue broker:** Redis
- **Background jobs:** Celery + Celery Beat
- **Auth:** JWT (SimpleJWT) plus device tokens
- **File storage:** S3-compatible (receipts, logos, exports)
- **Server:** Gunicorn behind Nginx, Docker containers
- **Monitoring:** Sentry, Prometheus/Grafana or a hosted equivalent
- **CI/CD:** GitHub Actions

## 3. Project Structure

```
config/                  # settings (base/dev/prod), urls, celery
apps/
  core/                  # base models, tenant manager, utils, audit
  accounts/              # users, roles, permissions, devices
  tenants/               # shops, branches, subscriptions, enabled modules
  catalog/               # products, categories, variants, units, barcodes
  inventory/             # stock, movements, purchases, transfers, audits
  sales/                 # carts, invoices, returns, holds, shifts
  payments/              # payment methods, transactions, reconciliation
  customers/             # customers, khata ledger, loyalty
  reports/               # aggregates, dashboards, exports
  notifications/         # WhatsApp, SMS, email, push
  billing/               # your SaaS plans, invoices to shops
  sync/                  # offline sync endpoints, change log
  tax/                   # tax rules, FBR-style invoice formats
  modules/               # industry plug-ins
    pharmacy/
    grocery/
    restaurant/
    clothing/
    mobile_shop/
    salon_clinic/
tests/
docker/
```

**Rule:** apps talk through service functions (`sales.services.create_invoice()`), never by importing another app's models directly or writing to its tables. This keeps extraction possible later.

## 4. Multi-Tenancy
- **Model:** row-level. Every tenant table has `shop_id` (and `branch_id` where relevant).
- **Enforcement:** an abstract `TenantModel` with a custom manager that auto-filters by the current shop from the request context. Raw unfiltered queries only via an explicit `unscoped()` method.
- **Safety net:** PostgreSQL Row-Level Security as a second layer, and tests that fail if any tenant model lacks the base class.
- **Module toggling:** `ShopModule(shop, module_key, enabled)`. A permission class blocks endpoints of modules the shop hasn't enabled.

## 5. Core Data Models

**tenants and accounts**
- `Shop`, `Branch`, `Subscription`, `ShopModule`
- `User`, `Role`, `Permission`, `Device`

**catalog**
- `Category`, `Product`, `ProductVariant`, `Barcode`, `Unit`, `PriceList`, `TaxRate`

**inventory**
- `StockItem` (per branch and variant)
- `StockMovement` (append-only: sale, purchase, return, adjustment, transfer)
- `Supplier`, `PurchaseOrder`, `PurchaseItem`, `StockTransfer`, `StockAudit`

**sales**
- `Invoice`, `InvoiceItem`, `InvoiceTax`, `HeldCart`
- `Return`, `ReturnItem`
- `Shift`, `CashDrawerEntry`

**payments**
- `PaymentMethod`, `Payment` (a split payment is several rows per invoice)
- `PaymentGatewayTxn`, `Reconciliation`

**customers**
- `Customer`, `LedgerEntry` (khata, append-only), `LoyaltyAccount`, `LoyaltyTxn`

**Industry modules**
- **Pharmacy:** `Batch` (number, expiry, cost), `Substitute`, `LooseUnitRule`
- **Restaurant:** `Table`, `Order`, `KitchenTicket`, `MenuItemModifier`
- **Mobile shop:** `DeviceUnit` (IMEI), `Warranty`, `RepairJob`, `InstallmentPlan`
- **Salon/clinic:** `Service`, `Appointment`, `Package`, `Membership`, `StaffCommission`
- **Grocery:** `WeighedItem`, scale settings
- **Clothing:** variant matrix (size/color), `ExchangeRule`, `SeasonalDiscount`

**Cross-cutting**
- `AuditLog` (who, what, when, before/after)
- `Notification`, `NotificationTemplate`
- `SyncChange` (change log for offline sync)

**Data rules**
- Money in `DecimalField` (or integer minor units), never floats.
- UUID primary keys, generated by the client where offline creation is needed.
- Stock and ledger are **append-only movements**; balances are derived or cached and reconcilable.
- Invoices are immutable once finalized. Corrections happen through returns or credit notes.
- Soft delete with `deleted_at` so sync can propagate deletions.

## 6. API Design
- **Versioned:** `/api/v1/...`
- **Style:** REST, JSON, cursor pagination, `django-filter` for filtering.
- **Key endpoints:**
  - `auth/login`, `auth/refresh`, `auth/device-register`
  - `catalog/products`, `catalog/barcodes/{code}`
  - `sales/invoices` (create is idempotent), `sales/returns`, `sales/shifts`
  - `inventory/stock`, `inventory/purchases`, `inventory/transfers`
  - `customers`, `customers/{id}/ledger`, `customers/{id}/payments`
  - `reports/daily`, `reports/profit`, `reports/stock-valuation`
  - `sync/pull`, `sync/push`
  - `modules/pharmacy/batches`, `modules/restaurant/tables`, and so on
- **Idempotency:** `Idempotency-Key` header (or client invoice UUID) on all create calls, so retries never duplicate.
- **Errors:** consistent error format with codes the app can translate into local languages.
- **Rate limiting:** per device and per shop.

## 7. Offline Sync Design
This is the hardest part, so design it early.

- **Client side:** local SQLite/IndexedDB holds products, customers, stock snapshot, and an **outbox** of pending actions.
- **Push:** the client sends queued operations (create invoice, add payment, adjust stock) with UUIDs and timestamps. The server processes each one atomically and idempotently, and returns per-item success or conflict.
- **Pull:** the client asks `sync/pull?since=<cursor>` and gets changes from the `SyncChange` log (created, updated, deleted) for its shop and branch.
- **Conflict rules:**
  - Sales and payments are append-only, so no conflicts. They are simply accepted.
  - Stock is computed from movements, not overwritten, so two offline devices selling the same item both apply cleanly (stock may go negative and raise an alert).
  - Editable records (product price, customer details) use last-write-wins with a version number, plus a warning flag on conflicts.
- **Invoice numbering:** each device gets its own prefix or number range, so offline invoices never collide. The server may assign a final fiscal number when synced.
- **Testing:** simulate two devices, long offline periods, duplicate submissions, and out-of-order delivery.

## 8. Authentication and Permissions
- Shop owner signs up, then creates staff with roles: Owner, Manager, Cashier, Stock Keeper, Accountant (and industry roles like Pharmacist or Stylist).
- Permissions are granular (`sales.void_invoice`, `catalog.change_price`, `reports.view_profit`) and assigned to roles.
- PIN-based quick login for cashiers at the counter, with full login for owners.
- Device registration and the ability to revoke a lost device.
- Optional 2FA (OTP over SMS or WhatsApp) for owners.
- Sensitive actions (void, big discount, price change) can require manager approval, and all are logged.

## 9. Background Jobs (Celery)
- Send WhatsApp/SMS receipts and payment reminders
- Near-expiry and low-stock alerts (daily schedule)
- Daily owner summary at a set time
- Report aggregation and materialized summaries
- Payment reconciliation with gateways
- Subscription billing, renewals, and grace-period checks
- Data exports (PDF/Excel) for large reports
- Database backup verification and data cleanup

## 10. Integrations
- **Payments:** local wallets and bank/QR APIs, isolated behind a `PaymentGateway` interface so each provider is an adapter.
- **Messaging:** WhatsApp Business API and SMS providers behind a `MessageProvider` interface.
- **Tax authority:** invoice submission and QR/fiscal number retrieval, handled with a retry queue since the authority's API can be slow or down.
- **Hardware:** the backend generates receipt payloads; printing and scale/scanner handling live in the client.
- **Accounting export:** CSV/Excel, later connectors.
- **Webhooks:** outgoing events for customers who want to integrate (invoice created, stock low).

## 11. Security and Compliance
- HTTPS only, secure headers, CORS locked to your apps.
- Password hashing (Argon2), short-lived access tokens, refresh rotation.
- Encrypt sensitive fields (API keys, tokens) at rest; secrets kept in a vault or environment manager, never in code.
- Tenant isolation tests in CI, plus PostgreSQL RLS.
- Full audit log for financial and permission changes.
- Backups: automated daily full plus point-in-time recovery, with restore drills.
- Follow local data protection rules, and give shops data export and deletion.
- Regular dependency scanning and rate limiting against brute force.

## 12. Performance and Scaling
- Correct indexes on `(shop_id, created_at)`, barcodes, and invoice numbers.
- `select_related`/`prefetch_related` discipline; query-count tests on hot endpoints.
- Cache product catalogs and settings in Redis.
- Report queries use pre-aggregated daily tables rather than scanning all invoices.
- Partition large tables (invoices, movements) by date once they grow.
- Read replica for reports when needed.
- Horizontal scaling: stateless app containers behind a load balancer, separate Celery worker pools.

## 13. DevOps and Environments
- **Environments:** local (Docker Compose), staging, production.
- **Pipeline:** lint, tests, security scan, build image, deploy, run migrations.
- **Migrations:** backward-compatible only (add, then backfill, then remove later) so deploys never break live shops.
- **Config:** environment variables, feature flags for gradual rollout.
- **Logging:** structured JSON logs with shop and request IDs.
- **Alerts:** error rate, queue backlog, slow queries, failed syncs, failed reconciliations.

## 14. Testing Strategy
- Unit tests for services (tax, discounts, stock, ledger math).
- Integration tests for API flows (sell, return, sync).
- Tenant isolation tests on every endpoint.
- Load test a busy shop (for example, 50 invoices per minute) and a sync burst after long offline.
- Property-style tests for money rounding and stock consistency.

## 15. Build Roadmap

**Phase 0 (weeks 1-2): Foundation**
Project setup, Docker, CI, base models, tenant manager, auth, roles, audit log.

**Phase 1 (weeks 3-6): Core POS**
Catalog, inventory movements, invoicing, payments, returns, shifts, customers and khata, basic reports.

**Phase 2 (weeks 7-9): Sync and reliability**
Sync push/pull, idempotency, conflict handling, device management, and heavy offline testing.

**Phase 3 (weeks 10-12): First industry module**
Pharmacy or grocery (batches and expiry, or weighing and khata), plus notifications and WhatsApp receipts, owner daily summary.

**Phase 4 (weeks 13-16): Launch readiness**
Subscription billing, tax invoicing, backups, monitoring, security review, pilot with 3 to 5 shops.

**Phase 5 (after launch): Expansion**
Add restaurant, salon/clinic, mobile shop, and clothing modules one at a time. Add analytics, loyalty, multi-branch, and webhooks. Extract a service only if a measured bottleneck appears.

*These are rough timings for a small team of 2 to 3 backend developers; adjust to your team.*

## 16. Key Risks and Mitigations
- **Sync bugs and data conflicts:** design append-only data and idempotency first, and test offline heavily.
- **Tenant data leakage:** base manager, RLS, and mandatory isolation tests.
- **Scope creep across six industries:** ship one module, then add others.
- **Tax and payment API changes:** adapters and retry queues.
- **Downtime hurting shops:** offline mode, staged deploys, and backward-compatible migrations.
- **Slow reports as data grows:** pre-aggregation and partitioning early.
